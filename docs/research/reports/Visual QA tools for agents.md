# Measure with scripts, judge with vision

An agent can check a responsive page without a human using a stack that costs nothing and needs no account: **Playwright** for capture and emulation, **pixelmatch or odiff** for change detection, **axe-core** (with the WCAG 2.2 tag switched on) for accessibility, and a hand-written `page.evaluate` probe for overflow, image scaling, clipping, overlap and 44px targets, because no maintained library does that last job well. Playwright is already a dependency of this repo with Chromium and WebKit cached locally, so the starting cost is zero downloads. The wrappers people usually reach for are a poor fit in late 2026: BackstopJS is unowned with no release since 2024, Lost Pixel was archived in April 2026, and Argos, Percy and Chromatic are hosted services capped at 5,000 screenshots a month. Every tool in this stack answers a narrow question, and none answers "is this layout good": pixel diffs only say something changed, DOM geometry reports roughly one finding in four that no human can see, and accessibility engines find somewhere between 30% and 57% of issues. The evidence on vision models is consistent across studies from 2024 to 2026: they are coarse approximators, within one point of human ratings on a 7 point scale about three quarters of the time, about 90% right when two designs differ clearly, near chance when they differ slightly, and poor at locating what they criticise. The reliable division of labour is therefore to compute every measurable fact by script, hand those numbers to the model alongside cropped and sparsely marked screenshots, and treat the model's design opinion as advice that never gates a release on its own. Captures belong on the Mac or a separate runner pointed at the `*.pages.dev` preview, not inside the Cloudflare Pages build.

## Playwright plus a diff engine does the capture work; the wrappers are stale or metered

**Playwright 1.65.1 (Apache-2.0, published 2026-11-13)** is the one free tool that covers capture, emulation and comparison with no account ([npm](https://www.npmjs.com/package/playwright)). Arbitrary widths come from `viewport` or `page.setViewportSize()`, and the same context options emulate `reducedMotion`, `colorScheme`, `forcedColors`, `contrast` and `javaScriptEnabled: false` ([Playwright emulation docs](https://playwright.dev/docs/emulation)). Its `toHaveScreenshot` assertion waits until two consecutive screenshots match, disables CSS animations, CSS transitions and Web Animations, hides the caret, and accepts masks and an injected stylesheet ([Playwright PageAssertions](https://playwright.dev/docs/api/class-pageassertions)). Two limits matter for this site. First, that animation switch covers only those three mechanisms, and the site animates with GSAP, which runs in JavaScript; the notes infer (untested) that `[data-reveal]` content can be captured mid tween or still hidden unless the run emulates reduced motion, scrolls the page first, or forces the final state with a stylesheet. Second, baselines are valid only on the machine class that made them: Playwright states that rendering varies with "host OS, version, settings, hardware" and names baselines per browser and platform ([Playwright visual comparisons](https://playwright.dev/docs/test-snapshots)). The safe pattern is to capture both sides of a comparison in the same run on the same machine, for example the main preview against the branch preview. Whether `fullPage` triggers lazy images is unsettled; third party guides disagree and no official statement was found, so a scroll pass before capture is the conservative choice.

For the comparison itself, two engines are actively maintained. **pixelmatch 8.0.0 (ISC, 2026-10-06)** is tiny pure JavaScript; version 8 moved to a perceptual OKLab metric and added a `windowSize` option that reports the densest cluster of changed pixels, so scattered noise stays low while a compact real change stands out ([pixelmatch releases](https://github.com/mapbox/pixelmatch/releases)). **odiff 4.5.0 (MIT, 2026-07-23)** is a native Zig binary that its maintainer benchmarks at 1.17 s against 7.71 s for pixelmatch on full size screenshots, and it returns a distinct `layout-diff` reason when image sizes differ plus the row indexes that changed ([odiff README](https://github.com/dmtrKovalenko/odiff)). That benchmark is the maintainer's own; no independent speed or accuracy comparison exists. pixelmatch treats a size mismatch as an error, so a page that grew taller yields no localised diff; the script should record width and height per viewport first, since a height change is itself the most useful responsive signal. looks-same 10 (MIT) is slower moving but uniquely returns bounding rectangles of the changed regions, which gives an agent something to crop ([looks-same README](https://github.com/gemini-testing/looks-same)). Resemble.js declares "ultra low-maintenance mode", needs native `canvas`, and by default skips pixels on images over 1200px ([Resemble.js README](https://github.com/rsmbl/Resemble.js)).

The wrappers add little and cost a lot. BackstopJS (MIT) runs fully offline, but its last npm release was 2024-09-07, its README says it "needs a new maintainer/owner", it compares with Resemble.js and it pins Puppeteer 22 ([BackstopJS README](https://github.com/garris/BackstopJS), [npm](https://www.npmjs.com/package/backstopjs)). Lost Pixel's repository was archived on 2026-04-22 ([Lost Pixel](https://github.com/lost-pixel/lost-pixel)). reg-cli (MIT, active) compares two folders and builds an HTML report but does not capture ([reg-cli README](https://github.com/reg-viz/reg-cli)). Argos, Percy and Chromatic each allow **5,000 screenshots a month** free and all need an account ([Argos pricing](https://argos-ci.com/pricing), [Percy plans](https://www.browserstack.com/docs/percy/overview/plans-and-billing), [Chromatic pricing](https://www.chromatic.com/pricing)). Percy counts each page at each width in each browser as one screenshot, so a sweep of this site's roughly 228 URLs at six widths is about 1,368 screenshots, and the free tier covers about three full runs a month. That does not fit an agent that iterates many times a day, and it also sends unreleased client media to a third party.

None of this should run inside the Cloudflare Pages build. The build image documentation lists languages and package managers and never mentions a browser, and the free plan allows 500 builds a month with a 20 minute timeout ([Pages build image](https://developers.cloudflare.com/pages/configuration/build-image/), [Pages limits](https://developers.cloudflare.com/pages/platform/limits/)). No source confirms or denies Chromium running there, so assume it does not. For a contact sheet, `sharp.composite()` (Apache-2.0, prebuilt binaries) or an HTML grid screenshotted by Playwright itself both work with nothing extra installed ([sharp composite docs](https://sharp.pixelplumbing.com/api-composite/)); one sheet per route across all widths serves a reviewer better than one giant sheet.

## Layout defects are a custom probe job, and one geometric report in four is invisible

A pixel diff cannot find a defect on a page that has no approved baseline, and it defends a bad baseline as faithfully as a good one. Layout defects on a fresh page have to be measured from the DOM, and here the tooling is thin. The classic systems, Galen and ReDeCheck, are Java and Selenium projects with no commits since 2019 and 2018 ([Galen](https://github.com/galenframework/galen), [ReDeCheck](https://github.com/redecheck/redecheck)). No maintained npm library finds the overflowing element on a page; only gists exist. Lighthouse dropped its `content-width` and `tap-targets` audits ([Lighthouse default config](https://github.com/GoogleChrome/lighthouse/blob/main/core/config/default-config.js)). The one active newcomer, **renderlint** (MIT), renders at phone, tablet and desktop widths, sweeps the widths between, and reports clipped text, overflow, overlap and contrast as JSON for agent loops ([renderlint README](https://github.com/ngocanhnckh/renderlint)); it is worth a trial, but its claims are the vendor's and nothing independent measures its accuracy. Boxy has no detectable licence and should be treated as unusable.

The measurements themselves are standard DOM. Page overflow is `documentElement.scrollWidth > documentElement.clientWidth`, the test MDN itself documents ([MDN scrollWidth](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollWidth)); the culprit is the deepest element whose bounding rect passes the viewport edge, after excluding intentional scrollers and off canvas drawers. Pseudo elements have no rect, so the element scan can come back empty while the page still scrolls. For images, an upscale shows when rendered width times device pixel ratio exceeds `naturalWidth`, and a crop fraction falls out of comparing the box ratio with the natural ratio. This probe matters because **Lighthouse's `image-aspect-ratio` audit skips every image whose `object-fit` is not `fill`**, so a `cover` crop is never reported ([Lighthouse source](https://app.unpkg.com/lighthouse@12.6.1/files/core/audits/image-aspect-ratio.js)). Lighthouse 13 does still report `unsized-images`, `image-size-responsive` and cumulative layout shift ([Lighthouse default config](https://github.com/GoogleChrome/lighthouse/blob/main/core/config/default-config.js)), and the same shift data, with the shifted nodes named, is available in page through a `layout-shift` PerformanceObserver ([MDN LayoutShift](https://developer.mozilla.org/en-US/docs/Web/API/LayoutShift)). Lab runs under-report it because they perform only a basic page load ([web.dev Optimize CLS](https://web.dev/articles/optimize-cls)). These probe recipes are assembled in the research notes from standard behaviour, not taken from a tested tool, and one detail (how `scrollWidth` behaves when `overflow-x: hidden` sits on `html` versus `body`) needs an empirical check in Chromium.

Tap targets split in two. **axe-core's `target-size` is the only automated implementation of WCAG 2.5.8** (24 by 24 CSS pixels with the spacing exception), it is disabled by default, and Lighthouse runs the same rule ([axe-core rule descriptions](https://github.com/dequelabs/axe-core/blob/develop/doc/rule-descriptions.md), [W3C Understanding 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). No free tool checks 44 by 44, which is this site's own button spec, so that is a few lines of custom rect measurement at the mobile viewport. Spacing and alignment are the weakest area: no maintained free tool verifies a rendered page against a grid or checks gap consistency without being told the expected values. Because the site has spacing tokens, checking that computed gaps and paddings belong to the token set is exact and cheap; measuring rendered gaps between siblings is a heuristic that will flag intended asymmetry.

The research literature sets the expectation for how far any of this can be trusted. ReDeCheck, run on 26 real pages, produced **196 true positive reports, 48 false positives and 83 "non-observable" issues**, meaning DOM overlap or protrusion with no visible effect, and found 33 distinct failures ([ISSTA 2017 tool paper](https://eprints.whiterose.ac.uk/116991/1/c49.pdf)). That is about 60% precision if the invisible reports count as wrong. The follow up paper calls this "a fundamental limitation of all DOM-based tools" and fixes it by confirming each report visually: change the opacity of one element, screenshot again, compare ([STVR 2021](https://eprints.whiterose.ac.uk/165542/8/stvr.1756.pdf)). The same work shows why three device widths are not enough: failures appear in narrow ranges, such as one visible at 983px but not 1298px and a Bootstrap regression visible only at 766 to 767px ([ISSTA 2017 tool paper](https://eprints.whiterose.ac.uk/116991/1/c49.pdf)). These figures come from float and Bootstrap era pages, and how they hold on flexbox and grid layouts is not established. The transferable design is clear all the same: sweep many widths including each breakpoint plus and minus one pixel, group findings by width range, and confirm each geometric finding against pixels before reporting it. What no measurement decides is intent: whether an overlap is designed, whether a crop cut off the subject, whether whitespace feels balanced.

## Accessibility engines catch a third to a half and stop at images, focus and motion

**axe-core 4.14.1 (MPL-2.0)** is the engine nearly every free tool wraps, and it reliably decides contrast on flat backgrounds, missing names, and ARIA and landmark errors ([axe-core rule descriptions](https://github.com/dequelabs/axe-core/blob/develop/doc/rule-descriptions.md)). Two coverage figures circulate and they measure different things. Deque reports that axe-based automation found **57.38% of issues by volume** across more than 2,000 audits, a figure dominated by colour contrast, which was 30% of all issues ([Deque coverage report](https://www.deque.com/automated-accessibility-coverage-report/)). UK government guidance, drawn from a test of 13 tools against 142 planted barriers, says the best tools find **about 30 to 40%** of known issues ([GDS tool audit](https://tnaqa.mirrorweb.com/ukgwa/20260506110838mp_/https://alphagov.github.io/accessibility-tool-audit/), [DWP accessibility manual](https://accessibility-manual.dwp.gov.uk/tools-and-resources/automated-accessibility-testing)). For a dark themed site with text over media, the lower figure is the realistic one, because the contrast cases axe can settle are the flat background ones. In Deque's own data, focus order, focus visibility and non-text contrast were found only by manual testing ([Deque coverage report](https://www.deque.com/automated-accessibility-coverage-report/)).

Contrast over images and gradients is the clearest blind spot. axe "will not report on text elements that have a background-image" and returns those nodes as incomplete ([Deque color-contrast rule](https://dequeuniversity.com/rules/axe/4.9/color-contrast)); its maintainers say the problem "is better handled with screen shot testing" ([axe-core issue 708](https://github.com/dequelabs/axe-core/issues/708)). No maintained free package was found that does this. The notes propose a method built from Playwright primitives: take axe's incomplete contrast nodes, screenshot each box with the text made transparent, sample the background pixels, and compute the WCAG ratio against the worst case and the median pixel. This is a construction, not a published tool, and WCAG gives no formal rule for which pixel to use, so "worst case" is a conservative convention.

The other engines add less than their names suggest. Lighthouse's accessibility category is a subset of axe turned into a weighted score; its real value is the performance, SEO and image audits. Pa11y adds HTML_CodeSniffer as a second engine and scripted actions before the test ([pa11y README](https://github.com/pa11y/pa11y)); its LGPL-3.0-only licence is fine for a dev tool. IBM Equal Access (Apache-2.0) is the only independent, non axe rule engine, so disagreement between it and axe is a useful review signal ([accessibility-checker](https://npmjs.com/package/accessibility-checker)). The checks none of them perform are scriptable in Playwright as measured facts: a reduced motion run that confirms nothing is still animating (for GSAP, by diffing two screenshots a second apart, since media emulation proves nothing unless the script reads the preference), a JavaScript disabled run that confirms headings, copy and images are present without the reveal scripts, and a Tab loop that records each focused element and its box. No benchmark was found for how well a scripted focus check agrees with human auditors.

## Vision models approximate human ratings but fail on close calls and on location

The published evidence supports using a vision model as a coarse reviewer and nothing more. In the largest rating study (30 interfaces, 9,296 human responses, each model run ten times with the median taken), models matched the human rating exactly 35 to 38% of the time and landed **within one point on a 7 point scale 72 to 77% of the time**; when asked to pick the better of two designs they scored about 60% overall, about 90% when the human score gap was large and only slightly above 50% when it was small ([Luera et al., arXiv 2510.08783](https://arxiv.org/pdf/2510.08783)). Per factor agreement was weak for the things a layout review cares about: for Claude 3.5 Sonnet, visual hierarchy correlated at -0.14 and ease of use at -0.05, against 0.62 for aesthetic pleasure. The authors conclude that models are "approximators, not replacements" and should not be used for validation near the end of a design process. A 2026 chapter reportedly finds near perfect agreement with experts on aesthetics for newer models, but it was seen only as a search summary and the conflict is unresolved ([ACM DL listing](https://dl.acm.org/doi/10.1007/978-3-032-30549-7_12)).

Written critiques show the same shape. Designers validated only 13.1% of the comments Gemini Pro Vision generated for the UICrit dataset; zero shot comment quality scored 0.31 against 0.75 for human designers ([Duan et al., arXiv 2407.08850](https://arxiv.org/html/2407.08850v3)). In a CHI 2024 study GPT-4's suggestions were 52% accurate, 19% partly accurate and 29% wrong, and **accuracy fell to 39% in later rounds as the design improved**, which led the authors to call it unsuitable as an iterative tool ([Duan et al., arXiv 2403.13139](https://arxiv.org/html/2403.13139v1)). The counterweight is breadth: in a screenshot only heuristic evaluation, GPT-4 found 73% and 77% of a master issue set where an average single expert found 17 to 18%, and repeat runs agreed about 95% of the time ([Zhong et al., arXiv 2507.02306](https://arxiv.org/html/2507.02306v1)). A model sees many candidate issues consistently; it cannot be trusted on which of them are real.

The failure modes are specific. Models locate badly: bounding boxes drawn on a plain screenshot overlapped designer boxes at an IoU of 0.004, and the best pipelines reach only about 0.36 ([arXiv 2407.08850](https://arxiv.org/html/2407.08850v3), [arXiv 2412.16829](https://arxiv.org/html/2412.16829v2)). They misjudge simple geometry, averaging about 58% on tasks such as whether two shapes overlap ([BlindTest, arXiv 2407.06581](https://arxiv.org/html/2407.06581v4)). Between 27% and 42% of GPT-4's false issues came from misrecognising interface elements and a similar share from misjudging standard conventions; it caught 43 to 50% of cross screen inconsistencies where experts caught 83 to 86% ([arXiv 2507.02306](https://arxiv.org/html/2507.02306v1)). Designers also reported over-applied guidelines and dismissed issues returning under another name ([arXiv 2403.13139](https://arxiv.org/html/2403.13139v1)). A recent benchmark adds that a judge inspecting only the first rendered view produces "fluent but weakly grounded criticism" ([UXBench, arXiv 2606.16262](https://arxiv.org/pdf/2606.16262)). One caution on the yardstick: the human raters in these studies agree poorly with each other (Fleiss kappa 0.10 to 0.29), so part of every reported gap is designer disagreement. No study covers marketing site design, brand fit, typography or dark themes specifically.

The practices with measured support are these. Few shot examples chosen by similarity lifted comment quality from 0.31 to 0.48. Coordinate labels on the screenshot edges or numbered patches improved localisation, while a full grid overlay made it worse than no overlay at all ([arXiv 2407.08850](https://arxiv.org/html/2407.08850v3)). Zoomed crops around each candidate region, separate calls for generating, filtering and validating, and a different model for refinement than for generation raised box accuracy threefold, though a validation pass sometimes removed valid comments ([arXiv 2412.16829](https://arxiv.org/html/2412.16829v2)). Pairwise comparison is dependable only for clearly different candidates. Repeating a judgement and taking the median reduces noise ([arXiv 2510.08783](https://arxiv.org/pdf/2510.08783)). A fixed rubric in which each finding must be tied to observed evidence, with a coverage gate, is the design UXBench uses ([arXiv 2606.16262](https://arxiv.org/pdf/2606.16262)). Numbered marks on regions let a model refer to them by id ([Set-of-Mark, arXiv 2310.11441](https://arxiv.org/abs/2310.11441)); WebMarker (MIT) is a small library for that, and Playwright's own `locator.boundingBox()` supplies coordinates as text ([WebMarker](https://github.com/reidbarber/webmarker), [Playwright Locator API](https://playwright.dev/docs/api/class-locator)). The step that follows most directly from the localisation results, giving the model measured rectangles, gaps, font sizes and contrast ratios next to the image so it never estimates them from pixels, is an inference; no paper found tests it directly.

## Conclusion

The tools sort into three layers by the kind of claim they can make, and the value lies in keeping the layers apart. Scripts produce facts (this element is 12px past the edge at 820px, this ratio is 3.1 to 1, this image is shown at 1.4 times its natural size). Pixel diffs produce a tripwire (these routes and widths changed, here). A vision model produces an opinion with about one point of noise. Problems start when a layer is asked for a claim it cannot make: a diff asked whether a page is good, a geometry scan reported without visual confirmation, a model asked to measure. The model's most defensible role is the one the research converges on from both directions, as the confirmation step for measured findings and the reader of the residue that scripts flag but cannot decide, such as axe's incomplete list, a cover crop percentage or an overlap that might be intended.

Two consequences are easy to miss. Because model accuracy falls as a design improves and sits near chance on small differences, an agent's critique loop needs a stop rule, must be allowed to answer "no issue found", and should be told the house decisions (the yellow final CTA, the off-white text) so it does not report them as defects. And the largest open questions here are empirical and local, not literature gaps: whether GSAP reveals capture cleanly under reduced motion on these pages, how `scrollWidth` behaves with the site's overflow rules, and whether renderlint's findings hold up against a hand probe. Each is an afternoon's test on the real site, and each decides more about the stack than any further reading would.
