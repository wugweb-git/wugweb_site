# Client brand in a studio case study: colour, icons and branded visuals

Researched 2026-11-19. Each finding is tagged OBSERVED (seen on a live page or in its HTML on 2026-11-19), STANDARD (normative or official text), GUIDANCE (a recommendation by a named author) or COMPUTED (a contrast ratio calculated for these notes with the WCAG 2 relative-luminance formula; not from a source). Free sources only.

## 1. Client colour: how studios theme each case study and keep the agency frame

### Takeaway
Among the pages inspected, the one clear pattern of per-case theming is one client colour used as the page ground with the studio's own text colour, type and navigation unchanged (Ragged Edge). Several other leading studios do not theme the page at all: they keep a neutral studio ground and let the client's colour arrive only inside the images.

### Cited Findings
- OBSERVED, Ragged Edge, Wise: the `<body>` tag carries an inline style `background-color: #9FE870; color: #181F1F;`. The ground is Wise's bright green, the text colour is a near-black. Navigation (Home, Partnerships, Approach, Happenings, Join, Contact), typefaces (ABC Diatype Expanded, Grit) and chapter structure (Overview, Define, Create, Commit) are the studio's. (Source: [raggededge.com/partnerships/wise](https://raggededge.com/partnerships/wise), HTML fetched 2026-11-19)
- OBSERVED, Ragged Edge, Monzo: same mechanism, `background-color: #FFD7F0; color: #181F1F;` (a pale pink ground). (Source: [raggededge.com/partnerships/monzo](https://raggededge.com/partnerships/monzo), HTML fetched 2026-11-19)
- OBSERVED, Ragged Edge, Gaia: same mechanism, `background-color: #F1E9DD; color: #181F1F;` (a warm off-white ground). (Source: [raggededge.com/partnerships/gaia](https://raggededge.com/partnerships/gaia), HTML fetched 2026-11-19)
- OBSERVED across those three Ragged Edge pages: exactly one client-derived colour is set at page level (the ground); the text colour `#181F1F` is identical on all three, so the studio varies one token per case and holds the other constant. (Sources: the three Ragged Edge pages above)
- COMPUTED: the Ragged Edge pairs are high contrast. `#181F1F` on `#9FE870` is 11.36:1, on `#FFD7F0` 12.94:1, on `#F1E9DD` 13.90:1. All three grounds are light, which is why one dark text colour works on every case.
- OBSERVED, Collins, Figma: the `<html>` tag carries `--color-background:#f8f8f7; --color-foreground:#140700`, the studio's own off-white and off-black tokens (`--color-off-white`, `--color-off-black`), not a Figma colour. The page is not themed with the client palette; client colour appears only in the gallery imagery. (Source: [wearecollins.com/case-studies/figma](https://wearecollins.com/case-studies/figma/), HTML fetched 2026-11-19)
- OBSERVED, Collins: the stylesheet defines the theme as a small token set (`--color-background`, `--color-foreground`, `--color-mid`, `--color-button-background`, `--color-button-foreground`, `--color-close-button-*`) that flips between a light and a dark arrangement. A two-token (ground, foreground) contract set on the root is the whole theming surface. (Source: [wearecollins.com/case-studies/figma](https://wearecollins.com/case-studies/figma/))
- OBSERVED, Koto, Bolt: no page-level client colour found in the HTML (the only hex in the markup is `#141414`). The case is sectioned Challenge, Strategy, Identity, Application, Outcome, and Bolt's "high-voltage palette" appears in the images, which show yellow, green, black, beige and red. (Source: [koto.com/projects/bolt](https://koto.com/projects/bolt), fetched 2026-11-19; page dated 2023)
- OBSERVED, Metalab, Upwork: the page markup marks elements with `data-themed="background-color"`, `data-themed="color"`, `data-themed="fill,color"` and `data-themed="stroke"`, and the page data carries `"themeColorHex":"#ffffff"` and `"theme":"dark"`. So the site has a per-page theme mechanism that recolours ground, text, SVG fill and stroke together; on this page the value is white, not Upwork green. (Source: [metalab.com/work/upwork](https://www.metalab.com/work/upwork), HTML fetched 2026-11-19)
- OBSERVED, Pentagram, Hyphen: the write-up describes the client palette in words rather than theming the page: "Neon green has been applied sparingly, used as an accent colour", against a monochrome palette. (Source: [pentagram.com/work/hyphen/story](https://www.pentagram.com/work/hyphen/story))
- OBSERVED, Wolff Olins, Uber: colour is treated as a strategic device named in the copy ("safety blue" as a signal of the safety commitment), not as page chrome. (Source: [wolffolins.com/work/uber](https://www.wolffolins.com/work/uber))

### Inferences
- Two families exist in practice. Family A (Ragged Edge): one client colour becomes the page ground; everything else stays the studio's. Family B (Collins, Koto, Pentagram, Wolff Olins as inspected): the studio ground never changes and the client palette is confined to media. Neither family lets the client's typeface or navigation replace the studio's.
- The agency frame is kept by holding constant: navigation, type family, text colour, grid, section vocabulary and credits layout. The variable is one colour, at most two (ground plus a foreground pairing).
- Ragged Edge's approach works with one fixed text colour only because every sampled ground is light. A dark-system studio doing the same would need either dark-enough client grounds for light text, or a per-case text-colour switch (see question 2).
- For a dark neutral system the lower-risk translation of Family A is client colour on bounded surfaces (a hero band, a screen backdrop, a stat numeral, a rule) rather than the whole page ground, because a full-page saturated ground removes the dark frame that identifies the studio.
- The Metalab markup suggests a practical implementation rule: tag the elements that follow the case theme (ground, text, fill, stroke) explicitly, so untagged elements stay on studio tokens by default.

### Gaps
- Tinted section grounds, duotone image treatments, coloured numerals and accent rules were named in the brief but could not be confirmed from HTML alone: Koto, Wolff Olins, DesignStudio and Mother Design render colour through scripts or images, so static inspection shows nothing. A visual (screenshot) pass is needed to document them.
- DesignStudio's Airbnb address now redirects to further.group ([further.group/work/airbnb](https://www.further.group/work/airbnb)); no theming data could be read from it. Mother Design's page is a script shell with no readable content. The Pentagram Mastercard address tested returned 404.
- No studio was found that publishes a written rule for "how many client colours per case study". The count of one page-level colour is an observation from three Ragged Edge pages, not a stated policy.
- Sample size is small (about eight pages). It supports "these patterns exist", not "this is how most studios do it".

## 2. Deriving a usable theme from a brand colour, with contrast limits

### Takeaway
WCAG 2.2 is the operative standard: 4.5:1 for normal text (SC 1.4.3), 3:1 for large text (SC 1.4.3) and 3:1 for meaningful graphics and control boundaries (SC 1.4.11), with no exemption for brand palettes outside the logo itself. OKLCH with relative colour syntax and `color-mix()` is the current recommended way to derive tints and shades from one brand value, and APCA is a useful second check on dark grounds but is not normative.

### Cited Findings
- STANDARD, WCAG 2.2 SC 1.4.3 Contrast (Minimum), Level AA: text and images of text need a contrast ratio of at least 4.5:1; large-scale text needs at least 3:1. (Source: [W3C, Understanding SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html))
- STANDARD, SC 1.4.3: large-scale text is at least 18 point, or 14 point bold; with 1pt = 1.333px that is about 24px regular or 18.5px bold. Thin or unusual faces may not behave as large text at those sizes. (Source: [W3C, Understanding SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html))
- STANDARD, SC 1.4.3: ratios are not rounded; 4.499:1 fails 4.5:1. The ratio is (L1 + 0.05) / (L2 + 0.05) on relative luminance, range 1:1 to 21:1. (Source: [W3C, Understanding SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html))
- STANDARD, SC 1.4.3 exceptions: logotypes (text that is part of a logo or brand name), incidental text (inactive components, pure decoration, invisible text, text inside a picture with significant other visual content). (Source: [W3C, Understanding SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html))
- STANDARD, SC 1.4.3 on brand colour: the logo exemption covers only logos and logotypes. Text that has low contrast because of corporate identity guidelines is not exempt. (Source: [W3C, Understanding SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html))
- STANDARD, SC 1.4.3: a background image with insufficient contrast behind text is a documented failure (F83). Colours are evaluated as specified in CSS, not as anti-aliased. (Source: [W3C, Understanding SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html))
- STANDARD, WCAG 2.2 SC 1.4.11 Non-text Contrast, Level AA: user interface components and "parts of graphics required to understand the content" need at least 3:1 against adjacent colours; 2.999:1 does not pass. (Source: [W3C, Understanding SC 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html))
- STANDARD, SC 1.4.11 exemptions: logos, flags, photographs of real scenes, screenshots and other essential presentations, pure decoration, inactive controls, and graphics whose information is also given in another form such as visible text. (Source: [W3C, Understanding SC 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html))
- STANDARD, SC 1.4.11: for gradients, test the least contrasting area that is needed to understand the object. Focus indicators must meet 3:1. (Source: [W3C, Understanding SC 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html))
- GUIDANCE, Evil Martians (Andrey Sitnik, Travis Turner; page dated 2025-09-17): HSL lightness is not perceptually consistent across hues, so "add 10% lightness" gives different visual results for blue and purple; OKLCH lightness is perceptual, which makes formula-generated palettes predictable. (Source: [Evil Martians, OKLCH in CSS](https://evilmartians.com/chronicles/oklch-in-css-why-quit-rgb-hsl))
- GUIDANCE, Evil Martians: derive variants from one source colour with relative colour syntax, for example `oklch(from var(--accent) calc(l + 0.1) c h)`; percentages do not work inside `calc()` here, so use `0.1`, not `10%`. (Source: [Evil Martians, OKLCH in CSS](https://evilmartians.com/chronicles/oklch-in-css-why-quit-rgb-hsl))
- GUIDANCE, Evil Martians: the page states that all backgrounds with L of 87% or more have good contrast with black text, so a lightness threshold can choose the text colour. The same page's changelog says OKLCH lightness alone is not enough and contrast should be checked with APCA. (Source: [Evil Martians, OKLCH in CSS](https://evilmartians.com/chronicles/oklch-in-css-why-quit-rgb-hsl))
- GUIDANCE, Evil Martians: LCH shifts blue towards purple when chroma is reduced (hues about 270 to 330); OKLCH holds hue when chroma changes. This matters when making a low-chroma tint of a blue brand colour. (Source: [Evil Martians, OKLCH in CSS](https://evilmartians.com/chronicles/oklch-in-css-why-quit-rgb-hsl))
- GUIDANCE, Evil Martians: not every L, C, H combination is displayable; browsers map out-of-gamut values, and Chrome and Safari clip rather than gamut-map by the specified method. Recommended pattern: an sRGB base plus a P3 value inside `@media (color-gamut: p3)`. Chroma stays below 0.37 in practice. (Source: [Evil Martians, OKLCH in CSS](https://evilmartians.com/chronicles/oklch-in-css-why-quit-rgb-hsl))
- GUIDANCE, web.dev (David A. Herron, 2025-12-11): build a theme from one `--base-color` in OKLCH; derive lighter and darker variants by scaling lightness, for example `oklch(from var(--action-color) calc(l * 1.15) c h)` and `calc(l * 0.9)`. (Source: [web.dev, Color themes with Baseline CSS features](https://web.dev/articles/baseline-in-action-color-theme))
- GUIDANCE, web.dev: tinted surfaces and borders by mixing the brand colour into the page ground in Oklab: `--surface-light: color-mix(in oklab, var(--background-color) 80%, var(--base-color));` and `--border-color: color-mix(in oklab, var(--base-color), grey);`. (Source: [web.dev, Color themes with Baseline CSS features](https://web.dev/articles/baseline-in-action-color-theme))
- GUIDANCE, web.dev: register theme custom properties with `@property` (`syntax: '<color>'`) so an invalid per-case value falls back to an `initial-value` rather than breaking the page. The article gives no contrast targets and no method for choosing text colour on a coloured ground. (Source: [web.dev, Color themes with Baseline CSS features](https://web.dev/articles/baseline-in-action-color-theme))
- GUIDANCE, Chrome for Developers colour guidance (as reported in search results, not opened directly): mixing with white or black tends to desaturate and produce washed-out tints and shades; combine a lightness adjustment with the mix and keep lightness adjustments under about 30%. (Source: [developer.chrome.com, modern web guidance: color](https://developer.chrome.com/docs/modern-web-guidance/guides/visual-design/color))
- GUIDANCE, APCA (Andrew Somers, Myndex): APCA predicts perceived lightness contrast, is polarity-sensitive (light text on dark gives negative values, dark on light positive), and is the candidate method for WCAG 3. Neither WCAG 3 nor APCA is a W3C Recommendation; APCA is not backward compatible with WCAG 2. (Source: [Myndex, apca-introduction](https://github.com/Myndex/apca-introduction))
- GUIDANCE, APCA Bronze levels: Lc 90 preferred for body text; Lc 75 minimum for body text (above 18px); Lc 60 for medium fluent text (above 24px); Lc 45 for large fluent text (above 36px); Lc 30 minimum for any spot text; Lc 15 the invisibility point for some people. Rough equivalents of WCAG 2's 3:1, 4.5:1 and 7:1 are Lc 58, 72 and 85. (Source: [Myndex, apca-introduction](https://github.com/Myndex/apca-introduction))
- GUIDANCE, APCA: WCAG 2 contrast "fails most with dark colors" and its results for dark-mode colours are described as relatively meaningless; APCA reports much lower contrast than WCAG 2 for dark pairs. (Source: [Myndex, apca-introduction](https://github.com/Myndex/apca-introduction))
- COMPUTED, illustrative brand colours used as text or line on a dark neutral ground `#191919`: bright green `#9FE870` 11.93:1 (passes everything); pure red `#E50914` 3.67:1 (fails 4.5:1 body text, passes 3:1 large text and non-text); pure blue `#0000FF` 2.05:1 (fails all); deep navy `#1A1F71` 1.24:1 (effectively invisible).
- COMPUTED, text on a saturated brand ground: on red `#E50914`, white is 4.79:1 and black is 4.38:1 (white passes, black narrowly fails); on orange `#FF6900`, white is 2.89:1 (fails even large text) and black is 7.27:1. The right text colour on a brand ground has to be calculated per colour; it cannot be assumed.
- COMPUTED, a dark neutral system's own pairs: `#f4f4f4` on `#191919` 15.99:1; `#bababa` on `#191919` 9.06:1; `#f4f4f4` on `#2b2b2b` 12.87:1; `#bababa` on `#2b2b2b` 7.30:1.

### Inferences
- A brand colour needs three derived roles, each checked separately: (a) ground (a band or backdrop), (b) ink (text, numerals, rules, icons drawn in the colour on the studio's dark ground), (c) tint (a low-chroma surface mixed into the dark ground). One raw hex rarely serves all three.
- For ink on a dark ground, dark brand colours (navy, deep blue, forest green, maroon) fail. The fix that keeps the brand recognisable is to hold hue and chroma in OKLCH and raise L until the pair reaches 4.5:1 (text) or 3:1 (large numerals, rules, meaningful icons); that lifted value is a per-case "ink" token, while the true hex is still shown on grounds, swatches and in the client's own assets.
- For a ground, pick the text colour by test, not by rule of thumb: compute both the studio light text and a studio dark text against the ground and take the one that passes 4.5:1; if neither passes (mid-luminance colours such as some reds and oranges with light text), restrict the ground to large text at 3:1 or to image-only use.
- A tint for section grounds on a dark system is best made as `color-mix(in oklab, <dark ground> 85 to 92%, <brand>)`: the result stays dark, so the studio's existing light text keeps passing, and the case still reads as coloured.
- Accent rules and numerals are the cheapest brand carriers: a large numeral only needs 3:1 (if it meets the large-text size) and a decorative rule has no requirement, though a rule that separates content meaningfully should be treated as 3:1.
- Because WCAG 2 over-reports contrast for dark pairs, any brand-on-dark pair that only just passes 4.5:1 should be checked again with APCA (aim for Lc 75 for body-size text, Lc 60 for 24px and above) before it is accepted.
- The client's logo is exempt from contrast rules, but a logo that disappears on the studio's ground is still a presentation failure; use the client's reversed or mono version or place the logo on a plate in its own ground colour.
- The gate can be automated: store one brand hex per case, compute ground, ink and tint at build time, and fail the build when any text pair is under 4.5:1 or any meaningful graphic pair is under 3:1.

### Gaps
- No source was found that gives a published, tested algorithm for "lift a dark brand colour until it passes on a dark ground while staying on-brand". The OKLCH lightness-lift method above is an inference from the Evil Martians and web.dev techniques.
- The Chrome guidance figure (keep lightness adjustment under about 30%) comes from a search summary; the page was not opened, so treat the number as unverified.
- Some secondary sites give different APCA thresholds (for example Lc 60 as a body-text minimum). The figures above are from the algorithm author's own introduction; the secondary figures were not used. One blog claims APCA was removed from the latest WCAG 3 working draft; this was not confirmed against W3C text.
- Evil Martians' statement that L of 87% or more always works with black text is the authors' claim with no WCAG figure attached; it was not independently tested here.
- No authoritative source on duotone image treatment and contrast was found.

## 3. Icons in editorial content

### Takeaway
Nielsen Norman Group's position is that an icon must first communicate meaning, that very few icons are universally understood, and that a visible text label should accompany every icon. In a case-study page that makes most icons decoration beside text, which accessibility guidance says should be hidden from assistive technology, while an icon that alone carries meaning must meet 3:1 and have a text alternative.

### Cited Findings
- GUIDANCE, NN/g (Aurora Harley, 27 July 2014): "icons must first and foremost communicate meaning"; brand personality through colour and style comes second. (Source: [NN/g, Icon Usability](https://www.nngroup.com/articles/icon-usability/))
- GUIDANCE, NN/g: only a few icons are near-universal (home, print, the magnifying glass for search). Most are ambiguous because they mean different things in different interfaces; hearts and stars are cited as varying by site. (Source: [NN/g, Icon Usability](https://www.nngroup.com/articles/icon-usability/))
- GUIDANCE, NN/g: a text label should accompany every icon, including standard ones, and labels should be visible at all times; hover-only labels add interaction cost and fail on touch. (Source: [NN/g, Icon Usability](https://www.nngroup.com/articles/icon-usability/))
- GUIDANCE, NN/g: the 5-second rule. If a fitting icon for a concept cannot be thought of within about five seconds, an icon is unlikely to communicate that concept. (Source: [NN/g, Icon Usability](https://www.nngroup.com/articles/icon-usability/))
- GUIDANCE, NN/g: benefits of icons are fast recognition for well-known ones, compactness, good touch targets, no translation need, and visual appeal that supports a consistent product family. Keep them simple and schematic because fine detail is lost at small sizes. Test recognisability (what do you expect this to mean) and memorability. (Source: [NN/g, Icon Usability](https://www.nngroup.com/articles/icon-usability/))
- GUIDANCE, NN/g: in one test a non-standard clock icon for history was clicked by no participant; the article's summary is "Obscure icon = wasted feature". (Source: [NN/g, Icon Usability](https://www.nngroup.com/articles/icon-usability/))
- STANDARD, W3C WAI Images Tutorial: an image is decorative when it is visual styling, when it is supplementary to link text, when it illustrates adjacent text without adding information, or when it is identified and described by surrounding text. Mark it with an empty `alt=""`, never omit `alt`, and prefer CSS backgrounds where possible. Only the author can decide, based on why the image is on the page. (Source: [W3C WAI, Decorative Images](https://www.w3.org/WAI/tutorials/images/decorative/))
- STANDARD, WCAG 2.2 SC 1.4.11: a stand-alone icon with no text is a graphical object and needs 3:1 against adjacent colour; for a single-colour icon the whole icon is the object. An icon whose information is also given as visible text is exempt, as is pure decoration. (Source: [W3C, Understanding SC 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html))
- GUIDANCE, design-system documentation (as reported in search results): Material system icons sit on a 24dp grid with keyline shapes (18dp square, 20dp circle, 20dp-tall rectangle) to keep proportions consistent across a set. (Source: [Material Design 2, System icons](https://m2.material.io/design/iconography/system-icons.html))
- GUIDANCE, Tabler Icons design guide: draw icons with a 2px stroke on a 24px grid. GitLab uses 1.5px for nearly all UI icons and notes that optical adjustment can justify leaving the grid for balance or clarity. (Sources: [Tabler, Icon design guide](https://docs.tabler.io/icons/design-guide); [GitLab Pajamas, Iconography](https://design.gitlab.com/product-foundations/iconography))
- GUIDANCE, Shopify Polaris: icon rules are a starting point, not a hard constraint; scale icon and stroke weight proportionally. (Source: [Shopify Polaris, Creating icons](https://polaris.shopify.com/design/icons/creating-icons))

### Inferences
- A decision test for each icon in a case study: remove the icon; if the reader loses information, it is informative (needs a visible label or text alternative and 3:1); if nothing is lost, it is decorative (hide it from assistive technology, no contrast requirement, and ask whether it earns its space).
- NN/g's research is about interface icons, not editorial pages. Applied to a case study, it argues against icon-topped "feature card" rows where abstract ideas (strategy, trust, scale) get an invented icon: those fail the 5-second rule and add noise.
- Icons do help in three editorial places: (a) wayfinding and controls on the page (play, pause, next, close, external link), which should come from the studio's set; (b) a repeated legend where the same glyph marks the same kind of item every time; (c) as exhibits, when the client's icon set is itself part of the work being shown.
- Two icon vocabularies should never mix in the same role. The studio's set (one family, one stroke weight, one grid) owns page chrome and controls. The client's icons appear only as content, inside a figure, on a specimen sheet, or inside UI screens, at their native stroke and colour. Using client product icons as bullets or section markers in the studio's layout blurs who is speaking.
- A specimen of the client's icon set is a picture of the work, so it falls under the essential/screenshot exemption of SC 1.4.11, but it needs a text alternative that says what it shows (for example "Icon set, 48 icons, 2px stroke on a 24px grid").
- Sizing next to text: design-system norms put the base icon at 24px with a consistent stroke; beside running text an icon is usually set near the text's line height and optically centred on the x-height or cap height. This sizing rule is practice knowledge, not from a cited source.

### Gaps
- No NN/g article was found on icon-set visual consistency (stroke, grid) or on icons as decoration in content pages. The consistency rules cited come from design-system documentation, several via search summaries; the Material page itself returned no readable body text, so its grid and keyline figures are second-hand.
- No source was found that addresses "client icon set versus agency icon set in a case study" directly. The separation rule above is an inference.
- No research evidence was found measuring whether decorative icons help or hurt comprehension of long-form editorial content.
- The NN/g article is from 2014; the list of universal icons may be dated (it says the hamburger icon was not yet universal).

## 4. Branded visuals and how identity and product case studies are sequenced

### Takeaway
Leading studios' identity case studies run context, then idea, then identity elements (mark, type, colour, supporting assets), then applications, then outcome; the order of the middle elements varies by project and the naming of chapters varies by studio. Product case studies bring the brand in through the interface itself.

### Cited Findings
- OBSERVED, Koto, Bolt (2023): five sections in order: Challenge, Strategy (the idea "Shockingly Simple"), Identity (new logo, custom type, a "high-voltage palette", motion and sonic branding, photography and illustration), Application (UI, campaigns, motion, sound, code; images include a billboard, illustrations, portrait photography and a data graphic), Outcome. (Source: [koto.com/projects/bolt](https://koto.com/projects/bolt))
- OBSERVED, Ragged Edge, Wise: chapters Overview, Define, Create, Commit, then "The different reality" (results). Define states the strategy and the idea ("The World's Money"). Create runs colour (the "vibrant green, a symbol of both money and progress"), Logo, Bespoke typeface (Wise Sans, 960 languages), Verbal identity, Tapestries (a graphic asset system), then a sub-brand. Commit covers product design and film and photography. Results close the page: conversions up 10%, 34% uplift in new users taking the account, share price up 58% in 12 months. (Source: [raggededge.com/partnerships/wise](https://raggededge.com/partnerships/wise))
- OBSERVED, Ragged Edge, Wise: each identity element gets a short named block (a label plus one or two sentences), for example "Logo. Redrawn to retain the equity in the fast flag, now built for scalability." The page holds about 42 images and 21 videos, so motion carries a large share of the brand expression. (Source: [raggededge.com/partnerships/wise](https://raggededge.com/partnerships/wise), HTML counts 2026-11-19)
- OBSERVED, Ragged Edge, Wise, product section: "We worked with the Wise product design team to create a scalable system that lives across every part of the digital product", with an accessibility claim ("exceeding WCAG 3.0 requirements"). Note: WCAG 3.0 is a working draft, not a standard, so that claim cannot be checked against a published requirement. (Sources: [raggededge.com/partnerships/wise](https://raggededge.com/partnerships/wise); status per [Myndex, apca-introduction](https://github.com/Myndex/apca-introduction))
- OBSERVED, Pentagram, Hyphen: order is title and one-line summary, tags, lead image, pull quotes, then narrative: background, culture, brief, idea (a unit derived from the crosshair of the letter H), name and wordmark, typography ("A bespoke stencilled-alphabet was created by applying this unit to the Gza typeface"), colour (monochrome with a neon green accent "applied sparingly"), applications (website headings, scroll bars, headers), then credits (Client, Sector, Discipline, Office, Partner). (Source: [pentagram.com/work/hyphen/story](https://www.pentagram.com/work/hyphen/story))
- OBSERVED, Collins, Figma: hero with title and one line ("Defining a new category and a new story"), a media gallery, project details (Program, Industry, Stage), story text built on the brand idea ("Nothing Great Is Made Alone"), impact, credits, then "Augments": named brand properties with thumbnails, including "UI-as-Identity", "Memory Marker", "Extensibility" and "High Expressive Ratio", then an impact figure. The page text carries no captions about colour or type; those are left to the images. (Source: [wearecollins.com/case-studies/figma](https://wearecollins.com/case-studies/figma/))
- OBSERVED, Wolff Olins, Uber: a strategy-led case. Sections run from the business problem through brand turnaround, culture, story and reach to results and a client quote. Identity elements are not itemised; colour appears once as "safety blue" and the system as a "design language that flexes across the 'mobility ecosystem'". Product enters as an in-app feature (Uber Travel). (Source: [wolffolins.com/work/uber](https://www.wolffolins.com/work/uber))
- OBSERVED, Metalab, Upwork: a product case tagged Project Type "Product" with deliverables "Vision & Strategy, UX Research, Product Design". The hero is a photograph of a laptop on a desk with the Upwork product on screen; the brand enters through the product UI, with no palette, logo or type section in the readable content. (Source: [metalab.com/work/upwork](https://www.metalab.com/work/upwork))

### Inferences
- A sequence consistent with every identity page inspected: context and brief, the idea in one line, the mark, typography, colour, supporting system (illustration, pattern, motion, icons, photography, verbal identity), applications, results, credits. Mark, type and colour change order between studios (Ragged Edge leads with colour; Pentagram puts colour after type), so order should follow which element carries the idea.
- Identity elements are shown as specimens, one element per block, each with a noun label and one or two sentences of rationale. That block form (label, short rationale, one large visual) is the reusable unit.
- Studios split on how much the copy explains: Ragged Edge and Pentagram name each element in text; Collins and Koto leave colour and type to the images. For accessibility and search, naming the typeface and colour in text is the stronger choice because images of palettes and specimens carry no machine-readable information.
- For product work the brand's presence is the interface: its colour, type, icons and components are visible in every screen, so a product case study can express the client brand without a dedicated brand section. Collins naming "UI-as-Identity" as a brand property supports treating product UI as brand evidence.
- When a studio did both brand and product for a client, the Ragged Edge model (brand elements in "Create", product system in "Commit") shows a workable hand-off: the identity is established first, then shown surviving in the product.
- Type specimens, palette swatches and logo sheets are images of the client's identity; they fall under the logo and essential exemptions for contrast, but every one needs a text alternative, and the palette values should also be printed as text beside the swatches.

### Gaps
- The sequence "idea, mark, type, colour, system, applications" is not stated as a rule by any source found; it is a synthesis from five pages.
- No studio page inspected had a readable, explicit palette block (swatches with values) or icon-set block in its text, so how leaders present those two specimen types could not be documented in detail. A screenshot pass is needed.
- DesignStudio (now at further.group) and Mother Design could not be read; the Collins gallery images are uncaptioned, so their content is unknown.
- No reliable written source on how pattern and illustration systems should be shown (crop size, repeat, number of examples) was found.

## 5. Screens on coloured grounds versus device mockups

### Takeaway
The free, citable evidence on this question is thin: practitioner opinion says angled or generic device mockups pull attention from the interface, and one guide recommends brand-matched backgrounds inside a case study, but no critic of standing or study was found. The claim that device-less screens on a brand-coloured ground are the better practice is a reasonable inference, not an established finding.

### Cited Findings
- GUIDANCE (practitioner opinion; headline and search summary only, article body returned 403): an article titled "Why Angled Mockups Fail to Communicate Your Design" argues that slanted device mockups detract from the work and stop it being shown at its best. (Source: [Design Buddies on Medium](https://medium.com/designbuddies/why-angled-mockups-fail-to-communicate-your-design-f8b2050ba778))
- GUIDANCE (vendor blog, via search summary): inside the case study, switch to brand-matched backgrounds for screenshots, on the argument that it shows the work can extend into marketing assets. The same guide recommends high-resolution (2x or 3x) captures. (Source: [Screenhance, How to Present Screenshots in Your Design Portfolio](https://screenhance.com/blog/portfolio-screenshots))
- GUIDANCE (opinion, via search summary): a UX Collective piece argues that the creative freedom of mockups has produced a disconnect between mockup scenes and real-world branding practice, and that billboard mockups in portfolios can mislead students about what is normal in the industry. (Source: [UX Collective, Using design mockups? Let's rethink that](https://uxdesign.cc/using-design-mockups-lets-rethink-that-bebdc7a892a1))
- OBSERVED, counter-example: Metalab's Upwork case opens with a photograph of the product on a real laptop on a desk, which is a photographed device in a setting, not a generic template mockup. (Source: [metalab.com/work/upwork](https://www.metalab.com/work/upwork))
- OBSERVED: Koto's Bolt application images are described as a billboard, illustrations, portraits and a data graphic; no UI screens are shown on that page even though UI is named as a touchpoint. (Source: [koto.com/projects/bolt](https://koto.com/projects/bolt))
- STANDARD: a screenshot is an essential presentation under SC 1.4.11, so the UI inside it is not subject to the 3:1 rule, but any caption or label the studio sets over or beside it is ordinary text under SC 1.4.3, and text over a coloured or image ground that lacks contrast is failure F83. (Sources: [W3C, Understanding SC 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html); [W3C, Understanding SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html))

### Inferences
- A device-less screen on a flat ground shows the interface at the largest size for a given area, with no perspective distortion and no third-party hardware styling competing with the client's brand; a device frame spends pixels on bezel. This is the practical argument behind the opinion pieces.
- The backdrop is the best single place to spend client colour in a dark studio system: it is bounded, it sits directly behind the client's own product, and it carries no studio text that must pass contrast. It gives the Ragged Edge effect inside a frame the studio still owns.
- The backdrop must separate from the screen. A white UI on a pale brand tint, or a dark UI on a dark tint, loses its edge; where the screen edge and ground are close in luminance, add a hairline or soft shadow, or pick the brand's contrasting colour for the ground. There is no WCAG requirement on this edge (the screenshot is exempt), so it is a legibility judgement.
- A device frame is still justified when the device is the point: a photographed real installation, a watch or kiosk form factor, or a hand-held context shot. A neutral, flat, front-on frame can also signal "mobile" versus "desktop" where aspect ratio alone is ambiguous.
- Generic rendered scenes (angled phones, floating laptops, mock billboards) add nothing specific to the client and risk implying applications that never shipped. A studio that shows only real screens and real photographs is on firmer ground for credibility.

### Gaps
- No Brand New (UnderConsideration) review or other named critic commenting on mockups could be found through free search; the search returned none. The brief's "what critics say" cannot be answered with an authoritative source.
- The Medium article body could not be opened (403), so its specific arguments and author name are unverified.
- No study was found that compares reader comprehension or preference for device-less screens versus device mockups.
- Whether the leading studios predominantly use device-less screens on coloured grounds could not be confirmed from HTML; a screenshot survey is needed.

## 6. Legal and permission practice for client logos, brand assets and confidential work

### Takeaway
Permission to show a client's name, logo and work should not be assumed from having done the job; the sources agree that the right needs to be written into the agreement and that a named case study warrants a specific sign-off. This is practice guidance from legal commentary, mostly UK, not legal advice, and the AIGA form's exact wording could not be retrieved.

### Cited Findings
- GUIDANCE, Sprintlaw UK (published 19 October 2026; UK law): express permission is usually needed before using a client logo on a website, deck or social post. A logo can be a trade mark, a copyright artwork and a signal of a business relationship, and paying or being paid for the work does not by itself grant marketing rights. (Source: [Sprintlaw UK, Using Client Logos on a UK Website](https://sprintlaw.co.uk/articles/client-logos-website-permission/))
- GUIDANCE, Sprintlaw UK: context changes the risk. A plain "our clients" listing differs from wording that implies endorsement or a wider relationship; unregistered brand rights can be protected through passing off where use misleads or damages goodwill. Risk is higher in regulated sectors (financial services, healthcare, education, professional services). (Source: [Sprintlaw UK](https://sprintlaw.co.uk/articles/client-logos-website-permission/))
- GUIDANCE, Sprintlaw UK: a permission clause should cover materials (name, logo, testimonials, screenshots, project images), channels (website, proposals, social, awards, PR, email, paid ads), purpose (promoting your own services, not implying sponsorship), approval process, the client's brand guidelines and current logo version, how confidentiality terms interact, and duration and withdrawal (how fast the client can require removal). Paid advertising should be agreed separately. (Source: [Sprintlaw UK](https://sprintlaw.co.uk/articles/client-logos-website-permission/))
- GUIDANCE, Sprintlaw UK: case studies carry more risk than logo walls because they can reveal commercial figures, internal problems, roadmaps or personal data. Approval should cover client name, logo, project description, metrics, quotes, screenshots and channels. Some confidentiality clauses cover the existence of the relationship itself. (Source: [Sprintlaw UK](https://sprintlaw.co.uk/articles/client-logos-website-permission/))
- GUIDANCE, Sprintlaw UK: if a client declines, an anonymised case study may be possible, but it must not reveal confidential details or make the client identifiable. (Source: [Sprintlaw UK](https://sprintlaw.co.uk/articles/client-logos-website-permission/))
- GUIDANCE, Sprintlaw UK: agreements that assign deliverables to the client may remove the studio's right to display the work, so a portfolio carve-out is useful. Screenshots may contain third-party content, and stock image or font licences may restrict promotional use. Named individuals in quotes or photos are personal data under UK GDPR; performance claims must be accurate and substantiated (CAP Code). (Source: [Sprintlaw UK](https://sprintlaw.co.uk/articles/client-logos-website-permission/))
- GUIDANCE, Sprintlaw UK, steps: review the contract for publicity, confidentiality and IP terms; classify each project as logo mention, anonymised case study or named case study; send the proposed content for written approval; store the approval record and diarise review dates. (Source: [Sprintlaw UK](https://sprintlaw.co.uk/articles/client-logos-website-permission/))
- GUIDANCE, AIGA (via search summaries; the pages themselves returned 403): the AIGA Standard Form of Agreement for Design Services is modular, not a single fill-in form; its general terms address payment terms, client changes and portfolio usage, and it offers several options for intellectual property ownership. (Source: [AIGA Standard Form of Agreement for Design Services](https://aiga.org/resources/aiga-standard-form-of-agreement-for-design-services))
- GUIDANCE, AIGA (via search summary): an AIGA article on work for hire urges designers to keep an absolute right to show the work in a portfolio or in advertising for their services, whatever other rights are transferred. (Source: [AIGA, Intellectual property: what does work for hire mean for designers](https://www.aiga.org/resources/intellectual-property-what-does-work-for-hire-mean-for-designers))
- GUIDANCE, RGD Canada (via search summary): under a copyright buy-out the client gets full rights to the work, but the designer can retain the right to use the work in their portfolio. (Source: [RGD, Copyright agreement form](https://www.rgd.ca/forms/copyright-agreement))
- STANDARD, relevant to presentation: client logos shown in a case study are exempt from WCAG contrast requirements (SC 1.4.3 logotype exception; SC 1.4.11 logo exemption), which removes any accessibility pressure to recolour a client's mark. (Sources: [W3C, Understanding SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html); [W3C, Understanding SC 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html))

### Inferences
- A per-case permission record is worth keeping as data alongside the case study: what may be shown (name, logo, screens, metrics, quotes), on which channels, who approved and when, and any withdrawal terms. It supports the "flagged screens" and "proof screens only" style of rules a studio may already run.
- Showing a client's logo in the client's own approved version and colours, unaltered, serves both the permission terms (brand guidelines, current version) and the design aim (the client's brand is expressed, not reinterpreted). Recolouring a client logo to match the studio's palette is the riskiest treatment on both counts.
- Using a client's palette to theme the case-study page is a lighter use than reproducing the logo, since a colour alone is rarely protected, but it strengthens the visual association with the client and so belongs inside the same approval.
- Client fonts need care: showing a typeface as an image specimen is different from serving the font file on the studio's site, which would need a web licence the studio probably does not hold. Use images or video for client type specimens.
- For confidential work the options are, in order of exposure: named case with approved screens; named case with redacted or flagged screens; anonymised case with brand colour, logo and identifying UI removed. In the anonymised case, client-colour theming should be dropped because the palette can identify the client.

### Gaps
- The AIGA Standard Form of Agreement and AIGA's work-for-hire article could not be opened (HTTP 403), so no exact clause wording, version or date is quoted. Everything attributed to AIGA here is from search-result summaries and should be verified against the documents.
- The main legal source is UK-specific. No equivalent free, authoritative source for India or the United States was retrieved; trade mark fair use, passing off and data protection rules differ by jurisdiction.
- No data was found on how common portfolio clauses, approval steps or withdrawal terms are in real agency agreements ("typical agreement terms" is supported only by legal commentary and templates).
- The font-licensing and colour-protection points in Inferences are general practice knowledge and were not sourced in this pass.
