## Horizontal overflow of the page: reliable detection methods (scrollWidth versus clientWidth, finding the offending element) and their false positives

### Takeaway
Page-level overflow is a one-line measurement (`document.documentElement.scrollWidth > document.documentElement.clientWidth`); finding the culprit needs a second pass over every element's bounding rect against the viewport width, and that pass has known blind spots (pseudo-elements, integer rounding, content hidden by `overflow-x: hidden`). No maintained library is needed for this; a short `page.evaluate` script is the standard approach.

### Cited Findings
- `scrollWidth` is "a measurement of the width of an element's content, including content not visible on the screen due to overflow"; it is an integer; it is measured like `clientWidth` (includes padding, excludes border, margin and vertical scrollbar); "It can also include the width of pseudo-elements such as ::before or ::after"; with no overflow it equals `clientWidth`. MDN's own example tests overflow with `element.scrollWidth > element.clientWidth`. — [MDN Element.scrollWidth](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollWidth) (fetched 2026-11-19)
- The common "find the culprit" recipe loops over `document.querySelectorAll('*')` and flags elements where `scrollWidth > clientWidth`; the author notes it also catches overflow that produces no visible scrollbar. — [David Walsh, Detect CSS Overflow Elements](https://davidwalsh.name/detect-overflow-elements) (via search summary, 2026-11-19)
- A second widely copied recipe flags every element whose bounding rect extends past the viewport width, which maps more directly to what causes the page scrollbar. — [mortenscheel gist](https://gist.github.com/mortenscheel/e6b6bec0860f6dd8cca99d4adf31c805); same idea in [joshwcomeau gist, forked from SSHari](https://gist.github.com/joshwcomeau/215a383add2ef61bb40a8c94318c99c3) (via search summary, 2026-11-19)
- A third-party write-up of a 375px probe script recommends `document.documentElement.clientWidth` as the baseline and not `window.innerWidth` (misleading under mobile emulation), and warns that a pseudo-element can cause overflow that an element scan misses, so pseudo-elements need a separate check. This is a blog, not a primary source. — [claudelab.net article](https://claudelab.net/en/articles/claude-code/mobile-375px-horizontal-overflow-pseudo-element-probe-script) (via search summary, 2026-11-19)
- A blanket `overflow-x: hidden` "hides the symptom but leaves the real overflow in place" and can break sticky positioning. — [Sizzy blog](https://sizzy.co/blog/fix-horizontal-scroll) (via search summary, 2026-11-19)
- Lighthouse no longer ships a page-width audit: `content-width` is absent from the default config on the main branch. — [Lighthouse default-config.js](https://github.com/GoogleChrome/lighthouse/blob/main/core/config/default-config.js) (fetched 2026-11-19)
- renderlint advertises detection of horizontal overflow and text running off a phone screen, across phone, tablet and desktop widths plus a sweep of widths in between. — [renderlint README](https://github.com/ngocanhnckh/renderlint) (fetched 2026-11-19; vendor claim, not independently tested)
- ReDeCheck's "viewport protrusion" failure type is exactly this defect (an element overflowing the viewport), detected by sampling viewport widths and comparing DOM coordinates. — [Walsh, Kapfhammer, McMinn, ISSTA 2017 tool paper](https://eprints.whiterose.ac.uk/116991/1/c49.pdf)

### Inferences
- Recommended two-step probe (standard DOM behaviour, assembled from the sources above, not a single cited recipe): (1) page test `docEl.scrollWidth > docEl.clientWidth` at each viewport width; (2) if true, for each element compute `getBoundingClientRect()` and flag those with `right > docEl.clientWidth + 1` or `left < -1`, then keep only the deepest flagged elements (an ancestor is usually flagged only because of its child).
- Known false positives for step 2: elements inside a container that itself clips or scrolls horizontally on purpose (carousels, tables in `overflow-x: auto` wrappers, marquee tracks), elements moved off-canvas on purpose (`translateX(-100%)` drawers, visually hidden skip links, `position: fixed` off-screen menus), and elements with `transform` animations caught mid-flight. Filter by walking ancestors for `overflow-x` of `hidden`, `clip`, `auto` or `scroll` before reporting.
- Known false negatives: (a) pseudo-elements and text nodes have no element rect of their own, so the scan can report nothing while the page still scrolls; (b) if `html` or `body` has `overflow-x: hidden`, the scrollbar is gone but content is silently cut off, and whether `scrollWidth` still reveals it depends on which element carries the rule, so the element scan in step 2 should run even when step 1 passes; (c) `scrollWidth` and `clientWidth` are integers, so sub-pixel overflow can show as a 1px difference or as none; use a 1px tolerance.
- The check must run at several widths, not three. ReDeCheck's core finding (see the last section) is that failures appear in narrow ranges between the usual device widths, so a sweep (for example every 60px plus each stylesheet breakpoint, plus or minus 1px) catches more than spot checks at 375, 768 and 1440.

### Gaps
- I did not find a W3C or MDN statement of the exact behaviour of `document.documentElement.scrollWidth` when `overflow-x: hidden` or `clip` sits on `html` versus `body`. This needs an empirical test in Chromium before the probe relies on it.
- The MDN page fetched does not document rounding beyond "An integer", so the 1px tolerance is engineering practice, not a cited rule.
- No maintained, dedicated open-source "find the overflowing element" npm library was found; only gists and snippets. `detect-element-overflow` (MIT, v2.0.0, 2025-03-20) takes a child and a parent and returns per-side overflow in pixels, which is a helper, not a page scanner — [detect-element-overflow README](https://github.com/wojtekmaj/detect-element-overflow).

## Images: shown above natural size, cropped by object-fit cover, changed aspect ratio; missing width and height attributes; layout shift (CLS via PerformanceObserver or Lighthouse)

### Takeaway
Upscaling, distortion, missing dimensions and layout shift are all measurable: Lighthouse 13 still has `image-size-responsive`, `image-aspect-ratio`, `unsized-images` and the CLS metric plus `cls-culprits-insight`, and the same numbers can be read directly in `page.evaluate` with `naturalWidth`, `getBoundingClientRect`, `devicePixelRatio` and a `layout-shift` PerformanceObserver. What cannot be measured is whether an `object-fit: cover` crop cut off something important; only the amount of crop is computable.

### Cited Findings
- Lighthouse default config (main branch, read 2026-11-19) contains `image-aspect-ratio` and `image-size-responsive` (Best Practices category, weight 1 each), `unsized-images` (Performance, diagnostics group, weight 0), `layout-shifts` (hidden group), `cls-culprits-insight` and `image-delivery-insight` (insights group), and the `cumulative-layout-shift` metric (Performance weight 25). — [Lighthouse default-config.js](https://github.com/GoogleChrome/lighthouse/blob/main/core/config/default-config.js)
- Lighthouse 13.0 (published 2025-10-10) replaced `layout-shifts` with `cls-culprits-insight` and `uses-responsive-images` with `image-delivery-insight`; `unsized-images` stayed as a separate diagnostic; `offscreen-images` and `font-size` were removed with no replacement. Tooling keyed to old audit IDs must be updated. — [Chrome for Developers, Lighthouse 13.0](https://developer.chrome.com/blog/lighthouse-13-0)
- How `image-aspect-ratio` actually decides (Lighthouse 12.6.1 source): `THRESHOLD_PX = 2`; it computes the display size the natural ratio implies and fails when the smaller dimension differs by 2px or more. It skips CSS background images, SVGs, images with natural size of 5px or less, images not displayed, and every image whose computed `object-fit` is not `fill`. So an `object-fit: cover` or `contain` image is never reported by this audit. — [lighthouse@12.6.1 core/audits/image-aspect-ratio.js](https://app.unpkg.com/lighthouse@12.6.1/files/core/audits/image-aspect-ratio.js)
- The public doc for the same audit says an image is flagged when the rendered ratio differs by "5 percent or more" from natural; this conflicts with the 2px constant in source. Treat the source as authoritative for the version in use. — [web.dev image-aspect-ratio (search summary)](https://web.dev/image-aspect-ratio); contradicted by [Lighthouse source](https://app.unpkg.com/lighthouse@12.6.1/files/core/audits/image-aspect-ratio.js)
- `image-size-responsive` compares the image's natural size with displayed size times device pixel ratio (the "ratio" in its output is DPR, not aspect ratio); users report the tolerance is tight for `srcset` widths. — [Lighthouse issue 11505](https://github.com/GoogleChrome/lighthouse/issues/11505) (via search summary, 2026-11-19)
- Setting `width` and `height` on an image lets the browser compute an aspect ratio before the image loads and reserve the space; images without dimensions are the first listed cause of CLS, followed by ads, embeds and iframes without dimensions, dynamically injected content, and web font swaps. Good CLS is 0.1 or less for at least 75% of visits; above 0.25 is poor. — [web.dev Optimize CLS](https://web.dev/articles/optimize-cls) (last updated 2025-02-07)
- Lab tools such as Lighthouse "usually perform a basic page load", so they may not capture the full CLS; field data covers the whole page lifetime and can be higher because of post-load shifts. — [web.dev Optimize CLS](https://web.dev/articles/optimize-cls)
- A `LayoutShift` entry exposes `value` (impact fraction times distance fraction), `hadRecentInput` (true if input happened within 500ms; these shifts are excluded from CLS), `lastInputTime`, and `sources`, an array of `LayoutShiftAttribution` objects giving `node`, `previousRect` and `currentRect` for the shifted elements. Observed with `new PerformanceObserver(cb).observe({ type: "layout-shift", buffered: true })`. MDN marks the API experimental with limited availability. — [MDN LayoutShift](https://developer.mozilla.org/en-US/docs/Web/API/LayoutShift) (fetched 2026-11-19)
- The `web-vitals` library (Apache-2.0, v6.2.3 published 2026-10-05) is the maintained wrapper for CLS measurement in page. — [npm web-vitals](https://registry.npmjs.org/web-vitals), [GitHub GoogleChrome/web-vitals](https://github.com/GoogleChrome/web-vitals)

### Inferences
- Direct measurements an agent can run per `<img>` after `img.decode()` or `complete === true` (standard DOM properties; the formulas mirror the Lighthouse source cited above):
  - Upscaled: `rect.width * devicePixelRatio > img.naturalWidth` (same for height), with a small tolerance. For `srcset`, `naturalWidth` reflects the chosen candidate (`img.currentSrc`), so the test must be repeated per viewport width and per DPR (Playwright `deviceScaleFactor` 1, 2, 3). SVGs must be skipped (no fixed raster size).
  - Distorted: computed `object-fit` is `fill` and `abs(rect.width / rect.height - naturalWidth / naturalHeight)` exceeds tolerance. This is the only case Lighthouse reports.
  - Cropped by cover: computed `object-fit` is `cover` (or `none`/`scale-down` in some cases); crop fraction = `1 - min(boxRatio, natRatio) / max(boxRatio, natRatio)` where `boxRatio = rect.width / rect.height`. With `cover` the upscale test must use the scale factor `max(rect.width / naturalWidth, rect.height / naturalHeight) * DPR > 1`, not width alone, because the hidden axis is scaled too.
  - Missing dimensions: `!img.hasAttribute('width') || !img.hasAttribute('height')`, softened by checking for a CSS `aspect-ratio` or explicit CSS width and height, which also reserve space.
  - CSS background images are invisible to all of the above; they need `getComputedStyle(el).backgroundImage`, a separate `Image()` load to get the natural size, and `background-size` parsing.
- For CLS in Playwright: inject the observer with `page.addInitScript` before navigation, sum `value` for entries where `hadRecentInput` is false, and keep `sources` to name the shifted nodes. Because load-only CLS under-reports, the script should also scroll the full page (to trigger lazy images and reveal animations) and wait for fonts before reading the total. This is Chromium only, which matches the constraint.
- Scroll-triggered reveal animations that use `transform` and `opacity` do not count as layout shifts, but ones that animate `top`, `margin` or `height` do; a site with GSAP reveals should expect the observer to stay quiet only if the animations are transform based.

### Gaps
- Automatic detection cannot tell whether a `cover` crop removed the subject (a face, a logo, a UI screenshot's key area). Only the crop percentage and which edges are cut can be computed; judging the content needs a human or a vision model.
- Automatic detection cannot tell whether an upscaled image actually looks soft; the ratio is a proxy. A 1.1x upscale of a flat illustration is fine, a 1.1x upscale of a UI screenshot with text may not be.
- I did not confirm the current tolerance constants of `image-size-responsive` in Lighthouse 13.6.0 source; the only evidence is a GitHub issue summary.
- I did not confirm from a primary page that `LayoutShift` is Chromium only (MDN's compatibility table was not in the fetched extract); it only says "limited availability".
- Whether `image-aspect-ratio` logic changed between 12.6.1 and 13.6.0 was not checked; the audit ID is still present in the default config.

## Overlapping or clipped elements and truncated text: techniques (getBoundingClientRect, elementsFromPoint, scrollHeight versus clientHeight) and open source libraries, with maintenance status

### Takeaway
The classic tools (Galen, ReDeCheck, VISER) are unmaintained and Java or Selenium based; the usable 2026 options on Playwright are a hand-written `page.evaluate` probe, the young MIT-licensed renderlint, and galen-ts for spec-style assertions. All DOM-geometry approaches share one hard limit, documented in the research literature: bounding boxes can overlap or protrude without any visible defect, so reports need a visual confirmation step.

### Cited Findings
- Galen Framework: Apache-2.0 (licence file in repo); spec language of relative constraints (`inside`, `near`, `below`, `aligned`, `width`, `height`, `absent`, `centered`), run through Selenium. Latest release galen-2.4.4 on 2019-03-15, last commit 2019-03-10; an awesome-list files it under "Legacy & Inactive Projects". It needs the developer to write the expected layout as an oracle. — [GitHub galenframework/galen](https://github.com/galenframework/galen), [releases API](https://api.github.com/repos/galenframework/galen/releases/latest), [ISSTA 2017 tool paper, related work](https://eprints.whiterose.ac.uk/116991/1/c49.pdf)
- galen-ts 0.1.3 (Apache-2.0, published 2026-04-15): TypeScript port that takes a Playwright `page` in `Galen.checkLayout()` and reads the same `.gspec` files. Supports `inside`, `near`, `centered`, `aligned` (horizontally and vertically), `width`, `height`, `absent`, `contains`, `count`, `on`, `text`, `css`. Gaps: no OCR, no bundled image comparison, no Rhino engine. README does not state a Node version. — [galen-ts README on jsDelivr](https://cdn.jsdelivr.net/npm/galen-ts@0.1.3/README.md)
- ReDeCheck (MIT, Java, Selenium; last commit 2018-11-24): detects five failure types without a hand-written oracle: element collision (two elements overlapping), element protrusion (overflowing the container), viewport protrusion (overflowing the viewport), small-range layouts (a layout that applies only for a very small number of viewport widths) and incorrectly wrapping elements (forced onto a new row for lack of horizontal space). It builds a "responsive layout graph" of visibility and alignment between elements, sampling widths uniformly (for example every 60px) and at stylesheet breakpoints, then binary-searching the exact width at which layout changes. — [ISSTA 2017 tool paper](https://eprints.whiterose.ac.uk/116991/1/c49.pdf), [GitHub redecheck/redecheck](https://github.com/redecheck/redecheck)
- "A fundamental limitation of all DOM-based tools": "while the bounding boxes of two elements may overlap on a page, their backgrounds may be transparent, and their respective content may thus appear as non-overlapping to a human viewer." — [Althomali, Kapfhammer, McMinn, STVR 2021](https://eprints.whiterose.ac.uk/165542/8/stvr.1756.pdf)
- VISER and VERVE confirm a DOM-reported overlap or protrusion by changing the opacity of the reported elements and comparing screenshots (VERVE adds histogram-based image comparison for wrapping and small-range failures). VISER repo: MIT, last push 2019-04-17. — [STVR 2021 paper](https://eprints.whiterose.ac.uk/165542/8/stvr.1756.pdf), [GitHub redecheck/viser](https://github.com/redecheck/viser)
- renderlint (MIT, Node 18.17 or later, repo pushed 2026-11-19, 686 stars): renders each page at phone, tablet and desktop widths and dark mode, "sweeps the widths in between", and re-checks with longer text and bigger numbers. Example rule output in its README: `text-clipped` ("Text is cut off by an overflow:hidden container (12px past the right edge)", reported "at 1024px"), `contrast`. Repo description lists overflowing text, low contrast, overlaps and broken responsive layouts. Output is plain text, JSON, Markdown or GitHub annotations; exits 1 on any error. — [renderlint README](https://github.com/ngocanhnckh/renderlint) (vendor claims; not run or benchmarked in this research)
- Boxy (`boxy-layout`): "Drop-in layout linter for Playwright", "Not pixel diffing". Baseline-free lint checks: Clipping (element extends beyond a parent with `overflow: hidden/auto/scroll`), Overlap (positioned elements where a high z-index element is clipped), Collapsed (near-zero width or height but has content), Off-screen (positioned element outside viewport). Baseline checks: sibling spacing, position, size change over 30%, visibility, CSS diff. GitHub reports no licence and 0 stars; last push 2026-05-20. — [Boxy README](https://github.com/LuptonM/boxy), [GitHub API](https://api.github.com/repos/LuptonM/boxy)
- detect-element-overflow (MIT, v2.0.0): `detectElementOverflow(child, parent)` returns `collidedTop/Bottom/Left/Right` booleans and `overflowTop/Bottom/Left/Right` pixel values (negative means gap). Aimed at dropdowns and tooltips. — [detect-element-overflow README](https://github.com/wojtekmaj/detect-element-overflow)
- The element-level overflow test `scrollWidth > clientWidth` (and by the same definition `scrollHeight > clientHeight`) is the documented way to tell that content does not fit its box; MDN's example applies it to a `text-overflow: ellipsis` element. — [MDN Element.scrollWidth](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollWidth)
- axe-core's `target-size` measures "the largest unobscured area of the touch target", so axe already contains an occlusion computation for interactive elements. — [Deque University, target-size 4.11](https://dequeuniversity.com/rules/axe/4.11/target-size)
- VisBug is an interactive browser extension (Apache-2.0); the repository is archived (last push 2026-08-03). It is not a headless checker. — [GitHub API GoogleChromeLabs/ProjectVisBug](https://api.github.com/repos/GoogleChromeLabs/ProjectVisBug)

### Inferences
- Probe recipes (standard DOM behaviour; reference pages not fetched this session: [MDN elementsFromPoint](https://developer.mozilla.org/en-US/docs/Web/API/Document/elementsFromPoint), [MDN getBoundingClientRect](https://developer.mozilla.org/en-US/docs/Web/API/Element/getBoundingClientRect), [MDN Range.getClientRects](https://developer.mozilla.org/en-US/docs/Web/API/Range/getClientRects)):
  - Truncated text (single line ellipsis): computed `text-overflow: ellipsis` or `overflow: hidden` plus `white-space: nowrap`, and `scrollWidth > clientWidth`.
  - Truncated text (multi-line clamp or fixed height): `scrollHeight > clientHeight + 1` on an element whose computed `overflow-y` is `hidden` or `clip`, or which uses `-webkit-line-clamp`.
  - Clipped by ancestor: element rect not fully inside the rect of the nearest ancestor with non-visible overflow (this is ReDeCheck's "element protrusion" and Boxy's "Clipping"). Sub-pixel integer rounding means a 1px tolerance is needed.
  - Text overflowing a visible-overflow box (text spilling out of a card): build a `Range` over the text node and compare `range.getClientRects()` against the container's rect; `scrollWidth` on the container also reveals it.
  - Overlap of siblings or unrelated blocks: pairwise rect intersection among elements that are not ancestor and descendant, with area above a threshold (ReDeCheck's "element collision").
  - Occlusion (is this text or button actually covered): sample points inside the rect (centre and corners inset by 1px) with `document.elementsFromPoint(x, y)` and check that the first hit is the element or a descendant. The element must be scrolled into view first; points outside the viewport return nothing. Elements with `pointer-events: none` are skipped by hit testing, so decorative overlays with that property will not register as covering.
- Expected false positives for geometric overlap, consistent with the "non-observable issue" category in the research: intentional layering (text over a hero image or video, badges on cards, sticky headers over content, negative-margin decorative overlaps, glass panels), transparent boxes whose content does not visually collide, elements mid-animation (run after animations settle or with reduced motion forced), and off-canvas menus. Intentional truncation (clamped card excerpts) also triggers the truncation test; it should be reported as information, not as a fault, unless the element is a heading, a price, a button label or similar.
- To cut false positives the way VISER does, an agent can add a cheap confirmation: screenshot the region, set one of the two elements to `opacity: 0`, screenshot again, and count changed pixels inside the intersection. That reintroduces pixels, but as a local confirmation of a measured finding and not as a baseline diff.
- Practical ranking for a Playwright on Node 22 stack: own probe script first (no dependency, full control of tolerances); renderlint worth a trial because it is MIT, active and built for agent loops, but it is young and its accuracy is unverified; galen-ts only if a written spec per component is wanted; Galen, ReDeCheck and VISER are reference designs, not dependencies.

### Gaps
- No accuracy figures (precision, recall) exist for renderlint, Boxy or galen-ts; none was found in their READMEs.
- renderlint's full rule list and its handling of intentional overlap were not read (only the README head). Its star count and activity are from the GitHub API, not a quality signal.
- Boxy's licence is unknown (GitHub detects none), which fails the "note licence" constraint until clarified.
- "Layout Lint" (an MCP server that runs Playwright analysers, listed on an MCP marketplace) and `yail259/peek` (successor to the deprecated rlint) appeared in search but were not verified: [mcpmarket listing](https://mcpmarket.com/server/layout-lint), [GitHub yail259/rlint](https://github.com/yail259/rlint).
- Cannot be detected automatically from measurements: whether an overlap is intended by the design; whether clipped content was meaningful; z-order mistakes where both elements are fully visible but in the wrong stacking order; text that fits its box but collides visually with a background image's busy area.

## Tap target size checks (WCAG 2.2 target size 24 by 24 minimum, and the 44 by 44 guideline): which tools check it and their limits

### Takeaway
axe-core's `target-size` rule is the one automated implementation of WCAG 2.5.8 (24 by 24 CSS px, with the spacing exception), and Lighthouse runs that same rule in its Accessibility category; it is off by default in axe-core and has no 44 by 44 mode, so the 44px guideline needs a custom measurement.

### Cited Findings
- SC 2.5.8 Target Size (Minimum), Level AA: "The size of the target for pointer inputs is at least 24 by 24 CSS pixels", except: Spacing (undersized targets are positioned so that a 24 CSS px diameter circle centred on each target's bounding box does not intersect another target or the circle of another undersized target); Equivalent (another control on the page does the same and meets the criterion); Inline ("The target is in a sentence or its size is otherwise constrained by the line-height of non-target text"); User Agent Control (size set by the browser and not modified by the author); Essential (presentation is essential or legally required). — [W3C Understanding SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- For overlapping targets, "the overlapping area should not be included in the measurement of the target size, except when the overlapping targets perform the same action or open the same page." The requirement does not apply to targets while they are obscured by content that appears through user interaction or scripting (dropdown, modal). It is measured in CSS pixels, so zoom cannot satisfy it. — [W3C Understanding SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- SC 2.5.5 Target Size (Enhanced) "uses the larger 44 by 44 CSS pixel measure as its threshold size". — [W3C Understanding SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) (the fetched page did not state the conformance level of 2.5.5)
- axe-core `target-size`: "Ensure touch targets have sufficient size and space"; impact Serious; tags `wcag22aa`, `wcag258`; issue type "failure, needs review"; listed under WCAG 2.2 Level A and AA rules, about which the doc says "These rules are disabled by default, until WCAG 2.2 is more widely adopted and required." — [axe-core rule-descriptions.md](https://github.com/dequelabs/axe-core/blob/develop/doc/rule-descriptions.md) (fetched 2026-11-19)
- How the rule measures: "Touch targets must be at least 24 by 24 CSS pixels in size"; "Size is computed by taking the largest unobscured area of the touch target"; an undersized target passes if a virtual 24px diameter circle centred on it "does not intersect any other targets, nor any of the circles on other undersized targets". — [Deque University, target-size 4.11](https://dequeuniversity.com/rules/axe/4.11/target-size)
- Deque's Wilco Fiers stated that few WCAG 2.2 criteria can be automated without false positives and that target-size is likely the only WCAG 2.2 rule to be added to axe-core. — [w3c-wai-gl mailing list, 2022](https://lists.w3.org/Archives/Public/w3c-wai-gl/2022OctDec/0129.html) (via search summary)
- Reported defects in the rule: an issue that target-size does not respect the inline exception for `display: inline-block` elements, and a user comment on issue 4387 that nearby obscured elements are mishandled. — [axe-core issues](https://www.github.com/dequelabs/axe-core/issues), [issue 4387 mirror](https://github.hscsec.cn/dequelabs/axe-core/issues/4387) (via search summary; user reports, not confirmed by maintainers in what I read)
- Lighthouse (main branch, 2026-11-19): `accessibility/target-size` is in the default config, Accessibility category, weight 7, group `a11y-best-practices`. The old mobile-friendliness audits `tap-targets` and `content-width` are absent. — [Lighthouse default-config.js](https://github.com/GoogleChrome/lighthouse/blob/main/core/config/default-config.js)
- Current versions: axe-core 4.14.1 (MPL-2.0, 2026-11-16), @axe-core/playwright 4.14.0 (2026-10-15), Lighthouse 13.6.0 (Apache-2.0, 2026-10-27). — [npm axe-core](https://registry.npmjs.org/axe-core), [npm @axe-core/playwright](https://registry.npmjs.org/@axe-core/playwright), [npm lighthouse](https://registry.npmjs.org/lighthouse)

### Inferences
- With `@axe-core/playwright` the rule has to be switched on explicitly, for example `new AxeBuilder({ page }).withRules(['target-size'])` or `.withTags(['wcag22aa'])`; a default axe run will not report tap targets. Results in `incomplete` ("needs review") must be read as well as `violations`, since the rule declares both issue types.
- The rule must be run at the mobile viewport with the mobile layout active; target size is layout dependent, so a desktop run says nothing about the phone layout.
- Since the Lighthouse audit path is `accessibility/target-size`, it is the axe rule and inherits the same 24px threshold and limits; Lighthouse no longer has any 48px or 44px tap-target audit.
- 44 by 44 (the site's own button spec and WCAG 2.5.5) is not checked by any free tool found. A custom probe is simple: for each interactive element (`a[href]`, `button`, `input`, `select`, `textarea`, `[role=button]`, `[tabindex]`, `summary`), take `getBoundingClientRect()`, skip inline links in running text, and flag width or height under 44. The hit area can be larger than the visible box if padding or a pseudo-element extends it; the element rect includes padding but not a pseudo-element's absolutely positioned hit area, so a rect-only check can under-report true hit area.
- What automation cannot decide for 2.5.8: the Equivalent exception (is there another conforming control for the same function), the Essential exception, and many Inline cases; and whether two overlapping targets "perform the same action".

### Gaps
- The conformance level of 2.5.5 (AAA, from general knowledge of WCAG) was not confirmed by a page fetched in this session.
- I did not read the axe-core source for `target-size` to list its exact exclusions (inline, native widgets, hidden, `pointer-events: none`) or its `incomplete` conditions; the Deque page fetched does not list them.
- No source found for how many real failures the axe rule misses or over-reports (no published precision or recall).
- renderlint's successor description mentions "tiny touch targets" in a search summary; its threshold was not verified.

## Spacing and alignment consistency checks: is there any tool that verifies alignment to a grid or consistent gaps?

### Takeaway
No maintained free tool was found that checks a rendered page for adherence to a grid or for consistent gaps without being told the expected values; what exists is either spec-driven (Galen and galen-ts assert stated offsets and alignment), baseline-driven (Boxy flags sibling gaps that changed since the last run), or source-level (stylelint plugins that restrict CSS values to a scale). A measured consistency check has to be custom built.

### Cited Findings
- Galen's spec language can assert alignment and spacing when the expected values are written down, for example `below header 0 to 5px`, `width 150 to 180px`, `inside viewport 0px top, 0px left, 0px right`, plus `aligned horizontally` and `aligned vertically`; galen-ts supports `inside`, `near`, `centered`, `aligned`, `width`, `height` on Playwright. — [galen-ts README](https://cdn.jsdelivr.net/npm/galen-ts@0.1.3/README.md)
- Boxy's spacing check is regression only: "Gap between siblings changed beyond threshold", compared with a saved baseline; it also reports position shifts and size changes over 30%. It has no absolute rule for what a gap should be. — [Boxy README](https://github.com/LuptonM/boxy)
- ReDeCheck's responsive layout graph models alignment relations between elements (left, top and bottom alignment over ranges of viewport widths) and reports where those relations change unexpectedly, which is alignment consistency across widths, not alignment to a design grid. Its false positives included alignment shifts among three elements wrongly classed as a "row" and reported as wrapping. — [ISSTA 2017 tool paper](https://eprints.whiterose.ac.uk/116991/1/c49.pdf)
- Source-level option: a stylelint plugin ("rhythmguard") enforces a spacing scale in authored CSS. It checks stylesheets, not the rendered result. — [DEV Community article](https://dev.to/petrilahdelma/enforcing-your-spacing-standards-with-rhythmguard-a-custom-stylelint-plugin-1ojj) (via search result title only; not read)
- An MCP server called "Layout Lint" lists "spacing and typography" among its issue categories. — [mcpmarket listing](https://mcpmarket.com/server/layout-lint) (via search summary; not verified, licence unknown)
- The search summary for this question stated it found no tool that explicitly checks grid-alignment consistency across a page. — search run 2026-11-19 (query: spacing consistency alignment grid rendered DOM tool open source "layout linter")

### Inferences
- A custom measured check is feasible because the site already has spacing tokens; the probe would (1) read the token values from `:root` computed style, (2) for each flex or grid container read computed `gap`, `row-gap`, `column-gap`, padding and child margins and flag values not in the token set, (3) measure actual rendered gaps between consecutive sibling rects (`next.top - prev.bottom` or `next.left - prev.right`) and flag a sibling group whose gaps differ from each other by more than 1px, (4) cluster the `left` edges of top-level section content and flag sections whose content edge is off the common container edge by 1px to 8px (a near miss is the tell for a mistake; a large offset is usually intended), (5) check that page content width never exceeds the stated max width.
- Such a check is a heuristic. It will raise false positives wherever the design intends optical alignment, full-bleed sections, asymmetry, or auto margins that distribute leftover space unevenly, so results should be labelled as "inconsistency to review".
- Computed-style token conformance (step 2) is more reliable than geometric gap measurement (step 3) because it is exact, but it only proves that tokens were used, not that the visual rhythm is right.

### Gaps
- I found no reliable source showing any free tool that infers a grid from a rendered page and verifies alignment to it. This is a real gap in tooling, not only in this search; the searches were limited to two queries on this point.
- No published accuracy data for any spacing or alignment checker.
- Cannot be detected automatically: optical alignment (an icon that is geometrically centred but looks off), whether whitespace feels balanced, and whether a deliberate break from the grid is a mistake.

## Academic or industry work on automatically detecting responsive layout failures, and how accurate it is

### Takeaway
The main body of work is the ReDeCheck line (Sheffield and Allegheny, 2015 to 2021): DOM-only detection found 33 distinct real failures on 26 production pages but only 196 of 327 reports were true positives, with 83 "non-observable" DOM-only issues, which is why later tools (VISER, VERVE) add a screenshot confirmation step. Recent work (ReFLAIR, 2025 to 2026) moves to multimodal models and claims large gains over prior tools, but none of this research ships as a maintained package.

### Cited Findings
- ReDeCheck common-failure mode, evaluated on 26 randomly collected real pages: 196 true positive reports, 48 false positive reports, 83 non-observable issues (DOM-level overlap or protrusion with no visible effect), spread over 137 distinct viewport ranges, amounting to 33 distinct responsive layout failures. "Well over half of the web pages, including well-known ones such as Duolingo and Consumer Reports, contained RLFs." A developer would need to inspect on average 4.2 viewport ranges per distinct failure. — [Walsh, Kapfhammer, McMinn, "ReDeCheck: An Automatic Layout Failure Checking Tool for Responsively Designed Web Pages", ISSTA 2017, Table 1b](https://eprints.whiterose.ac.uk/116991/1/c49.pdf)
- Search summary of the companion full paper gives the page count with failures as 16 of 26. — [Walsh et al., "Automated layout failure detection for responsive web pages without an explicit oracle", ISSTA 2017](https://www.cs.allegheny.edu/sites/gkapfham/research/papers/Walsh2017) (via search summary, 2026-11-19)
- ReDeCheck regression mode: on 100 modified versions of five pages (20 each, made by mutating width, margin or padding), 80 true positives, 12 true negatives, 0 false positives, 8 false negatives, recall 90.9%. — [ISSTA 2017 tool paper, Table 1a](https://eprints.whiterose.ac.uk/116991/1/c49.pdf)
- Runtime: "running in less than two minutes on most of the studied pages". A manual spot check at standard widths missed the Duolingo failure, which appeared at 983px but not at 1298px. Failures "often occur intermittently at unpredictable and occasionally small ranges of viewport widths"; in the Bootstrap case study a regression was visible only at 766 to 767px. — [ISSTA 2017 tool paper](https://eprints.whiterose.ac.uk/116991/1/c49.pdf)
- Stated limitations of ReDeCheck in 2017: reports use DOM references (XPaths) and are hard to read; dynamic pages that use JavaScript and whole-site checking were future work. — [ISSTA 2017 tool paper, section 5](https://eprints.whiterose.ac.uk/116991/1/c49.pdf)
- VISER (ICST 2019) automatically classified the 117 layout failures ReDeCheck reported for 20 web pages into true positive, false positive or non-observable, covering three of the five failure types. — [Althomali, Kapfhammer, McMinn, ICST 2019](https://eprints.whiterose.ac.uk/id/eprint/230100/1/althomali2019.pdf) (via search summary)
- VERVE (journal extension, Software Testing, Verification and Reliability, 2021, DOI 10.1002/stvr.1756) classifies all five types using opacity manipulation plus histogram-based image comparison; on 45 pages (25 from earlier studies plus 20 new) its classification "frequently agrees with classifications produced manually by humans", and it took "on average about 4 s to classify any of the RLFs among the 469 reported by ReDeCheck". Open access, tool stated as publicly available. — [Althomali, Kapfhammer, McMinn, STVR 2021](https://eprints.whiterose.ac.uk/165542/8/stvr.1756.pdf)
- The same paper names another DOM-based responsive testing tool, VFDetector, and says the non-observable problem "is not restricted to the use of ReDeCheck, but rather a fundamental limitation of all DOM-based tools". — [STVR 2021](https://eprints.whiterose.ac.uk/165542/8/stvr.1756.pdf)
- Walsh, McMinn, Kapfhammer (STVR 2020) regression comparison across two page versions detected 12.5% and 18.75% more injected changes than manual and automated baselines. — [White Rose eprint 163400](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf) (via search summary)
- ReFLAIR (He, He, Huq, Malek; DOI 10.1145/3808136, ISSN 2994-970X): multimodal generative AI approach that extracts informative and actionable widgets, compares them between the original and the reflowed layout, and uses scrolling plus model-guided expansion to find hidden widgets, targeting loss of information or functionality under WCAG reflow. On 24 pages it "improved precision by at least 20.49% and recall by at least 55.40%" over five existing techniques; extended to 36 pages over 28 domains with consistent results. — [CiteDrive record for ReFLAIR](https://www.citedrive.com/en/discovery/reflair-detecting-responsive-layout-reflow-issues-using-multimodal-generative-ai/) (abstract only; year and venue not shown on that page)
- XCOMPAT (arXiv 2608.12518): a detector for cross-environment rendering failures in pages generated by multimodal models, combining post-render DOM and a screenshot, with a page-level module for viewport and structural failures and a per-element module. — [arXiv 2608.12518](https://arxiv.org/pdf/2608.12518) (via search summary; metrics not read)
- A PNSQC 2025 industry paper reports over 95% detection accuracy for a ResNet-based Siamese network comparing rendered screenshots against design specs, ahead of pixel-difference, CLIP-embedding and DOM-diff baselines. This is screenshot comparison against a reference, not measurement. — [PNSQC 2025 paper](https://www.pnsqc.org/docs/PROP116612695-PNSQC2025-Shripad-CameraReady.pdf) (via search summary)
- Related earlier systems named in the ReDeCheck paper: X-PERT (cross-browser inconsistencies via relative layout), GWALI (internationalisation presentation failures), WebSee and Wraith (image comparison), Cornipickle (declarative layout constraints). — [ISSTA 2017 tool paper, related work](https://eprints.whiterose.ac.uk/116991/1/c49.pdf)

### Inferences
- From Table 1b, ReDeCheck's report-level precision is 196/327, about 60%, if non-observable issues count as wrong, or 196/244, about 80%, if they are set aside (my arithmetic from the cited table). Either way a DOM-only checker's raw output needs triage; roughly one report in four was an issue no human could see.
- No recall figure exists for common-failure detection on real pages, because nobody knows the full set of failures on those pages; the 33 failures are a lower bound on what was there. The 90.9% recall figure applies only to detecting injected CSS changes.
- The design lessons transfer directly to a Playwright probe even though the tools do not: sample many widths including breakpoints plus or minus 1px; model relations between elements (overlap, containment, same row) and look for widths at which a relation flips; group reports by viewport range to cut review effort; confirm each geometric finding visually before reporting.
- The 2025 to 2026 direction (ReFLAIR, XCOMPAT) is DOM measurements plus a vision model as judge. For an AI coding agent that already has vision, this suggests the workable pipeline is: measure, shortlist, then look at a cropped screenshot of each shortlisted region.

### Gaps
- Exact agreement rate between VERVE and human classification was not read (only "frequently agrees" from the abstract); the full 50-page paper has the tables.
- ReFLAIR's venue and year, the names of its five baselines, and whether code is released were not confirmed; only the abstract on an aggregator page was read. ISSN 2994-970X suggests an ACM journal (unconfirmed).
- XCOMPAT and PNSQC numbers come from search summaries only.
- I found no independent benchmark comparing the open-source rendered-UI linters of 2026 (renderlint, Boxy) with the academic tools, and no industry study quantifying how many layout defects DOM measurement catches versus human review.
- All academic accuracy numbers are for pages from 2015 to 2019 built largely on Bootstrap and Foundation floats and grids; how they hold on modern flexbox, grid and container-query layouts is not established in anything I read.
